# Requirements Document
Spec: `notebook-shelf`。
## Introduction
`notebook-shelf` は、`lab-notebook` のうち 1 つのセッションを見せるページ（表紙、ラボのページ、セッションのページ）を「ノートの棚」に置き換えます。1 つのセッションが 1 冊のノートで、その最初の画面で 1 つの話が完結します。`lab-notebook` のそれ以外はそのままです: 記録とその読み込み、インクの規則、目隠しのスキャン、フラットなサイト、画像シートと動く写真、語のリスト、インクの凡例ページ、「ラボのしくみ」ページ。
どの Kiro か: すべてのページは **ビルダー** が作り、**訪問者** が読みます。Dr. Kiro とリーダーはノートに触れません。人が書いた文（題、要約、写真の言葉）はビルダー自身の文で、オレンジのペン、ビルダーのレベルでスキャンします。
`lab-notebook` から置き換えるもの: 要件 8〜14 と 17 のうち古いレイアウトを述べる部分。リプレイ（16）はビルドに入れないまま（`lab-notebook` の Decision 48）。
そのまま適用する規則: `rules.md` の 1（目隠し）、2（早く止める）、4（正直）、5（言語）。状態の語はベンチの 4 つ。記録か choices のファイルにない数字は出さない。サイトは外へ通信しない。
## Requirements
### Requirement 1: 1 つの骨格に 2 つのアプリ
1. サイトの入口は短い表のページ。題の下の最初の行は英語のまま次の文: "Normally the spec judges the code. Here, the experiment judges the spec."（審査員が読むため、サイトは英語だけで書く。）題の下には、これ以外の標語を置かない。続けて、2 つのラボが 1 つの骨格（実験装置とノート）の上に乗り、それぞれが自分のノートを持つことを言い、アプリごとのカードを横に並べる: 昼の紙の風洞（CASE 1）と、夜の紙のロボット（CASE 2）。カードは、そのアプリが最初に開くセッションの動く写真（そのセッションの choices のファイルの最初の写真）を見せ、ラボが何か（`app.toml` の説明）を言い、そのセッションの題と 1 行を引き、アプリのセッションの数を数え、アプリのフォルダーへのリンク「Open the notebook」を持つ。題もリンク。訪問者が、比喩を読み解かなくても、カードからラボが何で、リンクがどこへ行くかが分かること。
1A. 入口はそれ自身のパレットを持たない。紙とインクはノートのもの（既定の夜のロウソクの紙）。各扉はそのラボのパレットをとる: 風洞は昼の紙、ロボットは夜の紙。
2. 各アプリはサイトのフォルダー `/wind-tunnel/` と `/body-lab/` で、自分のページ、絵、スタイルシート、スクリプトを持つ。その `index.html` は、設定が指すセッションのノート。アプリから表のページや別のアプリへのリンクは `/` と `/<application>/`。ほかのリンクはすべて相対で、`..` を含まない。
3. ノートを作るプログラムは 1 つ。アプリに属するものは、そのアプリ自身のフォルダー `<application>/notebook/` に置く: `app.toml`（順番、札と扉の文、説明、最初に開くセッション、1 回分の単位の語、開くテーマ、私たちのメモのペン、飾り）、choices のファイル、撮り直した絵のフォルダー。
4. 風洞は昼で開く: 明るい方眼紙、青いペン、きちんとした研究ノート、飾りなし（クモ、コウモリ、クモの巣、月、カボチャのどれもなく、ページに絵そのものがない）。ロボットは夜で開く: 真っ暗に近い机、ランプのように真ん中だけ明るい、大きな月、クモの巣、ぶら下がったクモ、コウモリ。その机の上に開いたノートは、昼のインクの白い紙で、部屋はハロウィン、ページは紙のノートのままにする（利用者、2026-11-22）。世界征服を企む科学者の狂気は、周りのアイコンではなく、ノートの紙そのものに残す: 上の縁から垂れる緑の薬品、紙の縁と下の角の焦げ跡。題は赤いインク（机の上の大見出しは明るい赤、紙の上のセッションの題は暗い赤）。綴じ目は、文字にかからない細く薄い糸の縫い目で、上の 2 つの角はボルトで留める。これらの跡は文字の下にあり、動かない。動くのはクモとコウモリだけ。2 つのラボのノートは同じ白い方眼紙（テンプレートそのものの紙）で、昼のノートの後ろの机は無地。どちらにもカボチャはない。テーマはアプリごとに 1 つで、切り替えはない: 風洞はいつも昼、ロボットはいつも夜。ロボットの机は、その上の文字が読める範囲でできるだけ黒に近い。
5. ページは、小さい見出し、大きな手書き風の題、アプリの説明 2〜3 行、各インクの意味を言う 1 行で始まる: 緑のインクは Dr. Kiro 自身の言葉、私たちのメモのペンは青（両方のアプリ、2026-11-22）、鉛筆は測った値。ノートのペンは 3 本: 緑は Dr. Kiro、青は私たちのメモ、赤は節の見出し、リーダーへの依頼の文、実験による直し（打ち消した規則の線、書き直しを下げる線、外れた予測の下の波線）。
6. アプリを切り替える札はない。ページの上に小さなリンクが 2 つ、英語で: "All labs" は入口のページへ、"Go to" に続けてもう 1 つのアプリの扉の題を置いたリンクは、そのアプリへ。見出しの下に、終わったセッションをノートの表紙のカードとして横に並べる。カードにはノートの題、1 行、小さい字で一番の結果と当たった予測の数、左に色の帯を出す。開いているカードは緑の枠で囲む。途中で止まったセッションは消さず、終わったセッションのあとに同じ行の小さなカードとして、途中で止まったと書いた 1 行とともに並べる。写っていないカードは暗くする。記録がボディの名前を持つセッションのカードには、小さく「changed body」と書く。
### Requirement 2: 開いたノート
1. 左にバインダーの穴、右上の隅にクモの巣。
2. ノートは「何が分かったか」を言い切る大きな手書き風の 1 行で始まり、次に 3〜4 行の要約が続く。
3. 題、題の後半、要約は、セッションの choices のファイル（`<application>/<session>.toml`）に人が書く。ページは読むだけ。要約は 40 語以内で、それより長いとビルドが失敗し、キーの名前を言う（切り詰めはしない）。ファイルがない、未知のキーがある、記録にない試行や測定を指す場合は、ファイルとキーを名指ししてビルドが失敗する。
4. 要約の下に小さい札: モデル名と日付（どちらも choices のファイルから）、記録がボディのラベルを持つときはそのボディ（記録の開始エントリーから。choices に `body` があれば一致しなければならない）、試行または実行の数、4 つの状態の語ごとの行数をアイコンつきで、予測の当たり数/全体。表が記録にないセッションは、4 つの数の代わりにそう書く。止まったセッションは、ベンチが記録した理由を出す。
5. アプリの最初のページ `index.html` は、`app.toml` の `open` が指すセッションのノート: 風洞は `wt-004`、ロボットは `body-3`。
6. セッションの副題と仮説の題は、筆記体ではなく本文の字（セリフ）で組む。ラボのページの大見出しは、セッションの題より小さい。副題は題の下の自分の行に置き、「our notes」の印は題の横に置く。印だけが 1 行に残ることはない。
7. ラボのページの最初の画面（1280 × 900 ピクセル）で、見どころの 2 枚の写真が見える: インクと名前の凡例（インクの説明と記号の行）は 1 行「How to read this notebook: the inks and the names」の下に畳み、セッションのカードは行を分け合う。
### Requirement 2A: ノートの意味
1. 見どころの後に、このセッションで起きたことを矢印でつないだ 3 つの段で言う。数字はすべて記録、表、リーダーの実行から数え、言葉はふつうの英語: Dr. Kiro が書いた予測の数（それぞれ実験の前）、外れた数と、取り消して書き直した規則の数、次の Kiro が spec から得るもの。
2. 3 つ目の段は、そのセッションのリーダーの実行が記録にあれば、リーダーがしたこと（「Another Kiro, given only this spec, did the task in 2 of 2 tries. With nothing, 0 of 2.」）を言う。なければ、spec のどの行を信じてよく、どの行が一部しか試されていないか、観察だけか、そして 2 人目の Kiro はこの spec で走らせていないことを言う。走らせていないリーダーを言うことはしない。最終の spec がない記録は、次の Kiro が読むものがまだないと言う。
3. リーダーの結果は、話の結末なので、この 3 つの段のすぐ下、発見した spec の前に置く。ノートの順番は: 題、要約、札、見どころ、What happened here、リーダーのテスト、発見した spec、Dr. Kiro のタスクと全部の実験。
4. 各節の頭に、それが何かを 1 行で書く。ただし見どころは、2 枚の写真と 3 つの数がそれを語るので書かない。H4 や R5 のような番号は小さな札で、カードの題はふつうの文。予測は「11 of 24 predictions, written before the run, came true」のように読める形にする。

### Requirement 3: 見どころと経過
1. 左にテープで留めた大きな写真が 2 枚。各写真には、人が選んだ大文字の小さい見出しと記録の仮説 id、人が書いた手書き風の一言、鉛筆の字で試行の id と測った値すべて。良い方には星。2 枚の絵は一緒に動く。下の 1 つの再生ボタンと 1 本のつまみで両方を動かし、各絵の下に、その時点で体がどこまで進んだか（「t = 3.0 s forward 38 cm」）を記録の track から出す。どの 2 つの試行かは人が選ぶ。写真、3 枚の付箋、グラフは、広い画面の 1 画面に収まる。
2. 右に、色違いで少し傾けた付箋が 3 枚。人が choices のファイルで、次のうち違う 3 つを選ぶ: 一番の結果、予測の当たり数/全体、rejected になった規則の数（記録に表がなければ Dr. Kiro が rejected とした仮説の数で、そう書く）、使った試行または実行の数、外れた予測 1 件（測った値と、予想した範囲）。数字はすべて記録から。ページの数字は短く（`+3.9 cm`、`0.75 m`、`cd 0.993`、e の表記なし）、記録の細かい値は開いたメモに出す。
3. その下の小さい枠に、試行ごとの「ここまでの一番」の線 1 本。線は、紙に鉛筆で描いたように少し揺れ、名前の付いた段は短い線で名前とつなぐ。縦軸は線の範囲に合わせ、線が枠の下に張り付かない。試行ごとの点は描かない。どの測定を使うか、高い方と低い方のどちらが良いか、試行が数えられるために等しくなければならない 2 つ目の測定（任意）は、人が choices のファイルで選ぶ。大きい伸びの段（全体の伸びの 10% 以上、多くて 4 つ）だけに、仮説と変化を短く書く（「H10: +9.2 cm」）。名前どうしは重ならない。比べ物の線は描かない（記録にない）。
4. 試行のないセッションでは 1〜3 の代わりに 1 文を出し、写真もグラフもない。
### Requirement 4: 発見した spec、タスク、全部の実験
1. 題は白に近いクリーム色の手書き風。人が書いた文は普通の字の色で、横に小さく、私たちのメモのペンの色で「our notes」と付ける。
2. 発見した spec は、表の 1 行につき 1 枚の詰めたカード。id、規則、範囲、状態の判子を持ち、ベンチが確かめたか否かの札がつく。`rejected` の行は規則に取り消し線を引き、書き直し先の行をリンクつきで隣に出す。範囲、実験、予測はカードの閉じたメモに入れる。
3. 「Dr. Kiro's tasks」が実験の背骨。まずベンチが宣言したセッションの目標を出し、次に記録にある最後の `tasks.md` のタスクの行を順に並べる。各行には、Dr. Kiro が付けたとおりのチェックの箱と、Dr. Kiro 自身の言葉。各行の下には、その行が名指す実験（`E3`、`E1 to E7`）または id（`H3`）の仮説のカードを置く。仮説は、それを名指す最初の行の下に置く。封印されたページでは、下の実験が走ったのに箱が空の行は、そう書く（「ran at the bench; the box was left empty」）。ベンチの前では spec のファイルは実行・判定・終わりのときだけ写されるので、最後の写しの後に登録され、まだ走っていない仮説は「Registered, waiting for its run」の下に置く。どの行も名指さない仮説は、リストの後に見出しを付けて並べる。記録にタスクのリストがなければ、そう書いて全部の仮説を並べる。
4. 仮説ごとに 1 枚のカード: 左に動く写真（新しい一番を出した試行、なければ最初の試行）、右に丸で囲んだ仮説 id、Dr. Kiro の題、予想、鉛筆の字で各予測の結果、その実験を引く表の行の判子、仮説の試行が新しい一番を出したとき（最初に数えられた試行は除く）は星つきの「new best」。行を押すと、Dr. Kiro の言葉そのまま、予測、判定、その仮説の全試行を載せたメモが開く。実験や予測へのリンクは、それを含むメモを開く。
5. 書き直された行（`rejected`）のカードは、左の帯を rejected の判子の色にし、規則に取り消し線を引き、書き直し先の行を隣に出す。判子は赤にしない。外れの赤は、外れた予測と測った値だけに、必ず「missed」の語と一緒に使う。
6. セッションの終わりの拒否は、表の上に 1 回だけ、1 つのブロックで出す。見出しは「the bench refused to end this session N time」（1 回）または「N times」（それ以上）で、各メッセージは記録どおり。引用に名前が出たカードには小さい琥珀色の印を付け、赤い箱は付けない（ラボのノートの要件 6.7）。
### Requirement 5: リーダー
1. セッションにリーダーの実行が記録されているとき、そのノートは、依頼の文と 3 つの結果を並べて出す: spec だけ、生の記録だけ、何も無し。それぞれ、実行数のうちの合格数と、失敗した実行も含めたすべての実行の結果を出す。
2. 依頼の文の下に 1 行、各実行の予算と合格の範囲を英語の形で出す: "each run: up to 12 trials · pass: x 0.3 to 0.5 m, heading -20 to 20 deg, y -0.2 to 0.2 m"。予算と単位は各実行の封印された開始エントリーから、範囲は依頼のファイルから取る。数字が取れないとき（実行ごとに予算が違う、宣言されていない測定を合格の範囲が指す、予算がない）はビルドが失敗し、ファイル名を言う。何も埋めない。
3. セッションの記録がボディのラベルを持つとき、同じボディで以前のセッションの spec を与えられたリーダーの実行を先頭に出す: 「Old spec, before the body changed: <session>」のタイルに、合格数と実行数、実行、その実行が頼った規則（そのセッションの表が述べるとおり）。別のボディで行った実行は、このセッションの節に出さない。
4. 3 つの列には見出しを付ける: 古い spec（同じボディで前に与えた spec、先頭、「Old spec, before the body changed」）、このセッションの新しい spec（「New spec, after the body changed」）、「No spec」。以前の spec がないボディのセッションは、spec の列を「Spec only」のままにする。
### Requirement 6: 撮り直した表示用の絵
1. body-lab の試行の記録の絵は小さい。`--display` でビルドに渡す表示用フォルダーには、封印された記録の外で撮り直した、選んだ試行の大きな絵を置ける。マニフェストが 1 枚ずつ名指しし、ビルドは `design.md` のとおりに確かめる。`--display` がなければ、どの試行も記録の絵を出す。ほかの代わりはない。
2. 撮り直した絵は、その試行が出るすべての場所で拡大した絵の代わりになる。封印された記録は変えない。
3. `notebook-retake` が撮る: 選んだ body-lab のセッションの各試行を、記録された入力からもう一度走らせ、記録の測定値と 1 つでも違えば止まり、そのあとで初めて、体を追う上からのカメラで、1 コマ 300px 以上、0.2 秒ごとに描く。アダプターも、実験装置が Dr. Kiro に返すものも変えない。
4. ノートのどの絵も、体の周りの大きな絵。記録の全体の絵は、ボタンを押したときだけ出す。風洞の絵は、記録のコマから体と渦のまわりを切り抜いて出す（走らせ直さない）。
### Requirement 7: 変えないこと
1. 目隠しのスキャンは、全ページ、スタイルシート、スクリプト、choices のファイルと cover のファイルのすべての文を対象にする。クラス名、コメント、属性の文もスキャンする。
2. ページ、絵、フォントはすべてサイト自身のファイル。`<div>` なし、外部への通信なし、インラインのスクリプトなし。
3. 新しいレイアウトに合わなくなったテストは変えてよい。通すためにテストを弱めることはしない。
