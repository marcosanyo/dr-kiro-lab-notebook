# 実装計画: lab-notebook

## Overview

ノートブックのビルドのタスクです。`requirements.md`（要件 1-22）と `design.md` から作りました。サブエージェントを 1 タスクにつき 1 つ割り当てるオーケストレーターが、「Run All Tasks」で実行します。順序はユーザーが決めたものです（要件の Decision 40）: マイルストーン 1（本物の記録から作るカバーと発見された spec の表。そのあと止まってユーザーに見せる）、マイルストーン 2（実験エントリー、停止したセッション、"How the lab works"、走行バンド）、マイルストーン 3（予測チャート、リプレイ、等しい試行キー、入力の線と軌跡）、そして "Built from the spec"、done-when のチェック、引き継ぎです。

どの Kiro か: すべてのタスクは **ビルダー** が行います。ここにあるものはどれも Dr. Kiro やリーダーには見えず、ビルドは `lab/` フォルダーに何も書きません。

## Notes for the user and for every sub-agent

- **どこで実行するか。** どのタスクも Docker とディスプレイを必要とせず、Kiro Web でもローカルでも動きます。ただし、ブラウザーでページを見せるチェックポイント（タスク 11、16、21）は、ユーザーの Mac で動かします。タスク 1.1 は 2 つのアダプターパッケージをパスでインストールします（設計 N23）。ある環境で `mujoco` や `wind-tunnel-model`（Gmsh）をインストールまたは import できなければ、**止めて報告します**。依存を外したり、スキャンを偽物にしたりしません。
- **「プロジェクトのチェック」**（"the checks"）とは、`notebook/` で `uv run pytest`、`uv run ruff check`、`uv run ruff format --check` が通ることです。すべてのタスクはチェックで終わります。Python 3.12 は `uv` 経由のみ（`tech.md`）。`notebook/uv.lock` はコミットします。
- **プロパティテスト**は `hypothesis` を 100 例以上で使い、`# Feature: lab-notebook, Property N: <title>` のタグを付けます。それぞれが独立したサブタスクで、テスト対象のコードの後に置き、`notebook/tests/properties/` に書きます。`wind-tunnel` と `lab-bench` の計画と同じく、この計画にオプションのタスクはありません。
- **本物の記録に対するテスト**は `notebook/tests/real/` にあり、コミット済みの `sessions/`、`notebook/choices/`、`notebook/layouts.toml`、スキャンのソースを読み、`tmp_path` にビルドします。そこで確かめる件数と id は、要件の introduction に挙げた記録の事実であり、ノートブックが主張する結果ではありません。
- **フィクスチャ**にはラベルが付きます: 宣言とすべての試行で `fake = true`、場所は `notebook/tests/fixtures/` か `tmp_path`、作るのは `build(..., allow_fake=True)` だけです（設計 N19）。フィクスチャの数値は、結果として示されることは決してありません（`rules.md` 4）。
- **変更しないもの**: `bench/`、`body-lab/`、`wind-tunnel/`、`sessions/`、`discovered/`、`docs/brief.md`、ルートの `README.md`、`.kiro/blind-scan/stop-list.txt`（要件 7.4）。タスクがベンチの変更を必要としそうなら、**止めて報告します**。
- **停止条件。** **Stop and ask（止めて確認）** のタスクはユーザーへの日本語の報告で終わり、ユーザーが答えるまで次のタスクは始まりません。停止条件に出会ったサブエージェントは報告し、決めません（`rules.md` 2、6）: 本物の記録に対するチェックの失敗（検査を通らない記録、表、画像、選択）、書き換えでは消せないビルダーレベルのテキストのスキャンの検出、設計の述べるとおりに振る舞わないベンチの関数、そして下の語のリストと画面のレビューです。
- **ブラインドのルール。** 部品、関節、アクチュエーター、ソルバーの名前を、ノートブック自身のテキスト（`text.py`、アセット、選択の理由）に書きません。ビルダーのテキストでのスキャンの検出は、除外リストではなく、言い換えで直します。
- **作り上げた数値なし。** サイトのすべての数値は、記録のフィールドか、設計が名指しする計算から来ます。
- **コミット。** タスクが変えたファイルだけを、1 つずつ名前を指定して、共著者の行なしでコミットします。
